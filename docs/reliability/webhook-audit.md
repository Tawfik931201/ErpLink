# Webhook reliability audit

Reviewed against the local working tree on 2026-11-03. This is source inspection and offline fault-injection evidence, not verification of deployed schema, provider delivery policies, runner availability, or database durability settings. Pre-existing architecture refactoring and sync-log changes were retained.

## Implementation follow-up (supersedes initial dispositions below)

The user subsequently authorized implementation against test connections. The queue now uses the additive migration `supabase/migrations/20261103155209_durable_webhook_execution.sql`:

- Each new receipt stores `erp_connection_id` and `connection_generation`; intake resolves these from a verified workspace/store association, and worker execution revalidates them.
- `dispatch_webhook_receipt` locks the receipt, creates one receipt-owned job and writes the permanent `queue_id` marker in one database transaction. A replaying dispatcher returns that same marker even after queue completion. No unlinked direct-insert fallback exists in the runtime intake/drain path.
- New receipt identities use `durable_version=2`; automatic pruning excludes them. Historic ambiguous jobs/receipts are retained for controlled recovery, rather than rebound to a guessed current destination.
- `claim_sync_job` separates retry timing from `lease_token`/`lease_expires_at`. Send Now bypasses retry scheduling, never an active lease or uncertain outcome. The SQL also serializes the same execution identity using a partial unique index and rejects claims blocked by an uncertain predecessor.
- Success, retry updates and heartbeat mutations carry the claim token. Heartbeats renew every 30 seconds. Expired leases and unknown ERP outcomes are parked (`outcome_unknown`, no automatic retry); a timeout does not cancel the original remote operation and therefore cannot justify replay.
- Destructive entity coalescing was removed from intake and batch selection. Each distinct accepted delivery remains a separate durable job. This increases work compared with the previous lossy optimization and requires operational capacity measurement.
- The worker runs inside the pinned ERP AsyncLocalStorage scope for both inbound and outbound flows. Business-effect idempotency is implemented separately by the ERP-effect work; this queue alone cannot prove remote exactly-once behavior.

Initial findings about dispatcher replay, Send Now stealing leases and destructive coalescing are therefore addressed in the new design, subject to deploying/verifying the migration and compatible application together. Reconciliation pagination/coverage, streaming request-size enforcement, best-effort terminal skip logging, unavailable source events and operator-led resolution of unknown outcomes remain separate limitations. Migration application and real SQL concurrency results must be recorded in the final report; source inspection or this mock model is insufficient proof.

New executable worker tests exercise 100 and 1,000 distinct jobs with mocked ERP work and real queue scheduling, asserting one invocation per job and correct pinned workspace/store/connection arguments. They also cover concurrent Send Now, expired leases, late-worker token fencing, uncertainty quarantine and definitive-failure lease release. Dispatch boundary tests cover 1,000 repeated calls for one receipt, dispatcher/network failure, and permanent-identity retention. SQL source pins include a negative self-check for removing the unleased/unknown claim guard. These are offline models and static SQL checks, not database load benchmarks.

## Actual architecture and data flow

Next.js App Router routes receive Zid, Salla, Shopify and Odoo deliveries. Runtime storage is Supabase JS REST backed by the SQL migrations in `supabase/migrations/`; there is no Redis/BullMQ/ORM queue. The service-role client bypasses RLS, making application scopes essential. See the companion tenant and ERP-routing audits for ownership boundaries.

| --- | --- | --- |
| Zid | `src/app/api/webhooks/zid/route.ts`: raw body, size check, `verifyZidWebhookAuthorization`, store/token workspace resolution, settings gate. Basic authorization is implemented in `src/lib/zid/webhook-auth.ts`. | `enqueueWebhookEvent` → durable inbox → queue → `processWebhookEvent` → preset/custom mapping → workspace ERP execution → logs/entity links. |

| Shopify | `src/app/api/webhooks/shopify/route.ts`: signature/topic/store resolution and settings gate. | Same durable queue; orphan receipts survive linking gaps. |
| Odoo record/stock | Scoped ingress authorization in `src/lib/odoo/webhook-secret.ts` before DB lookup. Record scope is mapping ID; stock scope is workspace ID. | Unbatched receipt → queue → `runBackgroundSync` in Odoo route / `processOdooStockEvent`. ERP values are read back; request values alone are not authoritative. |

These are implementation observations. Read-only official documentation was checked on 2026-11-03: [Zid webhook creation](https://docs.zid.sa/create-a-webhook?nav=1) documents username/password Basic authorization; [Salla webhooks](https://docs.salla.dev/421119m0) documents security strategies/signature headers. No signing strategy or registration was changed. Provider retry behavior for every response class has not been independently established, so a 503 permits recovery only where the sender actually resends.

`src/instrumentation.ts` boots in-process runners outside build/Vercel. `sync-queue-runner.ts` requires `SYNC_QUEUE_SELF_RUNNER=true` in production, drains known-workspace inbox rows, then processes queue rows every 30 seconds by default. Claims use a conditional update of due `next_retry_at` to a 15-minute lease. Processing defaults to 10 simultaneous jobs, 3 per workspace, batch 50. These limits are per invocation/process, not a distributed per-ERP limit.

## Existing recovery and its practical guarantee

The same batch fetch also had an unconditional delete of rows considered older. It now checks each row's version and schedule at deletion, preserving a concurrent merge or claim. A fifth queue execution test injects this change between fetch and deletion. This adds one conditional REST deletion per stale row; monitor backlog-drain latency before increasing batch limits.

`src/lib/ingress-batch.ts` had two independently reproduced defects: multi-row callers resolved after the first outcome rather than all outcomes, and rejected writes left batch promises unsettled. Both receipt and queue helpers now await every row and settle transport errors as explicit failures. Existing queue callers pass single rows, so the multi-row defect was latent at those call sites; no new production batching policy was introduced. The 18-case `ingress-batch-execution.test.ts` covers 100/1,000/10,000 mocked rows per helper, exact outcome counts/order and tenant payloads, no acknowledgement before commit, duplicates, DB/transport failure and recovery, plus immediate single-row callers. This is not end-to-end webhook throughput or real database durability evidence.

Durable receipt precedes queue insertion on the normal work path. A failed queue write leaves a pending receipt, and failed receipt persistence returns an error for retryable route responses. The queue uses exponential backoff/jitter, rate-limit/connection-error classifications, retry budget 5, frozen rows and archive-before-delete dead letters. A process crash leaves a leased row available again after expiry. Inbox dispatch stops after 10 failed attempts. Receipt uniqueness persists only while the receipt is retained. These mechanisms support at-least-once attempts within their operating assumptions; they do not prove exactly-once effects or that every accepted event reaches an ERP successfully.

Automatic reconciliation currently covers Zid order snapshots only. It cannot recreate every intermediate transition, Salla events, products, or undelivered events unavailable through provider reads. Orphans and stale Salla events are durable manual-recovery cases. Database outage before receipt commit is not accepted durable work; recovery depends on provider resend and externally configured retries. Odoo failure before receipt persistence has no established automatic source replay here.

## Verification

`tests/unit/queue-settlement-execution.test.ts` executes the real public workspace queue and archive functions using an in-memory fluent-query model, mocking engine/stock workers before import. No provider client or database is contacted. It injects merge-after-read and revival-during-archive boundaries. Before fixes, 2/3 cases failed (new payload deleted; revived row deleted). After fixes, unchanged success, concurrent merge, null-version merge and archive revival are covered. This model validates conditional query intent, not PostgreSQL concurrency semantics or live trigger behavior.

`sync-queue-races.test.ts` retains existing pins and strengthens deletion assertions to require CAS and reject the previous id-only await. The targeted run of this suite plus `queue-settlement-execution`, `ingress-durability` and `no-loss-regression` passed 55 tests before the additional null-version case. Final project gate results belong in `final-reliability-report.md`.

No real DB crash/restart, external ERP unknown-outcome recovery, production load, real merchant token rotation, multi-process throughput, schema/index deployment, or 10,000-event end-to-end rehearsal was verified here. No queue drain, refresh endpoint or live test was invoked.
