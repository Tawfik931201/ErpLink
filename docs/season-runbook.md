# دفتر تشغيل الموسم — طابور الإرسال إلى أودوو (محدَّث 2026-10-22)

> الهدف المتفق عليه: تسجيل كل الطلبات خلال ~30 دقيقة، والتأخير مقبول —
> الفقد الصامت مرفوض. كل الأرقام التالية للمسار الحالي (عملية واحدة).

## 0) قبل الموسم — الخطوات الإلزامية

0. **الفحص الذاتي للمسار** — الأهم قبل أول عميل حقيقي:
   `POST /api/admin/pipeline-selftest` بجسم `{ workspaceId, confirm: true }`
   (أو من لوحة الأدمن: "الفحص الذاتي للمسار"). يجب أن تنجح **كل** الخطوات.
   يشغّل المسار الحقيقي على بيانات وهمية وينظّفها.
1. **طبّق الترحيل**: `supabase/migrations/20261022_telegram_outbox.sql`
   (paste-ready، `BEGIN/COMMIT`). بدونه تضيع إشعارات التليجرام (المزامنة نفسها سليمة).
2. **سجّل كل 웹 هوك بالأسرار المشتقة** — بدونها كل حركة "legacy" تمرّ بسقف
   الـ120/دقيقة (الحد الوحيد الذي ما زال يردّ 429):
   - `POST /api/admin/zid-webhooks/refresh`
   - `POST /api/admin/salla-webhooks/refresh`
   - `POST /api/admin/odoo-webhooks/refresh` (create-before-delete)
   ⇒ بعد هذه الخطوات: **صفر رفض لأي طلب موثّق**.
3. **تأكد** `SYNC_QUEUE_SELF_RUNNER=true` (إلزامي — لا cron صالح على هذا الهوست).
4. **اربط تنبيهات الأدمن**: ضع `ADMIN_ALERT_WORKSPACE_ID=<مساحة إدارية>` في
   `.env`، واربط محادثتك بتليجرام في `/app/settings/notifications` لتلك المساحة.
   بعدها يصلك تنبيه واحد (مجمّع) عند أي خلل تشغيلي.
5. **بروفة**: `POST /api/admin/load-rehearsal` وضع `enqueue` (آمن في كل مكان).

## 1) قراءة الصحة: `GET /api/admin/queue-health` (أدمن فقط)

| الحقل | الطبيعي | خطر |
|---|---|---|
| `ready` | `true` | `false` = لا تدخل الموسم |
| `runner.ok` | `true` (`SYNC_QUEUE_SELF_RUNNER=true`) | `false` = الطابور يستقبل ولا يصرف أبداً |
| `migrations.ok` | `true` (الجداول + `dedup_key`) | `false` = طبّق `20260922` + `20260928` أولاً |
| `depth.pending` | < 500 خارج الذروة | > 2000 = تراكم يحتاج تدخلاً |
| `depth.frozen` | 0 | أي رقم > 0 = راجع شاشة الطابور وأعد التشغيل |
| `depth.orphans` | 0 | > 0 = متاجر بلا ربط — **زر «استرجاع الأيتام»** في `/app/queue` |
| `depth.inboxPending` | 0 | > 0 = مسار الإنقاذ يعمل (إدراج الطابور يفشل أحياناً) |
| `depth.inboxFailed` | 0 | > 0 = إيصالات توقفت بعد 10 محاولات — **تحتاج تدخّلاً** |
| `depth.telegramPending` | < 20 | > 200 = مُرسّل التليجرام متأخر |
| `depth.telegramFailed` | 0 | > 0 = رسائل استنفدت محاولاتها (مرئية الآن) |
| `depth.oldestPendingAgeSec` | < 300 | > 1800 = تجاوز نافذة الـ 30 دقيقة |
| `ingressAdmission.ceiling` | 120..2000 | السقف الديناميكي — ينخفض عند امتلاء الطابور |
| `ingressAdmission.overflow` | 0 | > 0 = عميل تجاوز حصته — **مقبول** (يُؤجَّل، لا يُرفض) |
| `ingressAdmission.rejectedUnauthenticated` | 0 | > 0 = حد الـIP للمجهولين — افحص المتاجر legacy |
| `ingressAdmission.rejectedGlobal` | 0 | > 0 = صمام الأمان العام أُغلق (20 ألف/دقيقة) |
| `circuitBreakers` | `[]` | عميل مركون = أودوو الخاص به ساقط |

## 2) مقابض الموسم (env على الهوست — تُرفع تدريجياً مع القياس)

| المتغير | عادي | موسم مقترح | ملاحظة |
|---|---|---|---|
| `SYNC_QUEUE_CONCURRENCY` | 10 | 25–40 | مرتبط بتحمّل أودوو/Supabase |
| `SYNC_QUEUE_BATCH_SIZE` | 50 | 100 | |
| `SYNC_QUEUE_MAX_PER_WORKSPACE` | 3 | 6–10 | للتاجر الساخن |
| `SYNC_QUEUE_POLL_INTERVAL_MS` | 30000 | 10000–15000 | لا تنزل عن 5000 |
| `SYNC_SEASON_MODE` | off | `true` في الموسم فقط | retry بعد 1/2/4/8/15 دقيقة **+ نافذة دمج 45 ثانية** |
| `SYNC_COALESCE_WINDOW_MS` | 0 | 45000 | نافذة الدمج: تحديثات نفس الطلب ⇒ كتابة واحدة |
| `SYNC_QUEUE_ITEM_TIMEOUT_MS` | 120000 | 120000 | مهلة الحدث الواحد |
| `SYNC_CB_THRESHOLD` / `SYNC_CB_COOLDOWN_MIN` | 10 / 15 | كما هي عادةً | عميل ميت يُركن بدل حرق الـ slots |

بعد الموسم: أعد `SYNC_SEASON_MODE` للإيقاف والمقابض للقيم العادية.

### لماذا نافذة الدمج مهمّة

`SYNC_COALESCE_WINDOW_MS=45000` تعني: الطلب ينتظر 45 ثانية قبل معالجته.
داخل هذه النافذة تتكدّس تحديثات نفس الطلب (تغيّر حالة، دفعة، شحن…) فتندمج
في **صف واحد** ⇒ **كتابة واحدة في أودوو بدل N**.

- ذروة 1000 تحديث لنفس الطلب ⇒ 5–10 كتابة بدل 1000.
- التكلفة: 45 ثانية تأخير — **مجانية** لأن الهدف 30 دقيقة.
- بدونها: كل تحديث = كتابة كاملة في أودوو (وطلب سحب من زد).

## 3) لو حصل تراكم أثناء الذروة (بالترتيب)

1. افتح `/app/queue` لكل عميل متأثر واضغط **إرسال الآن** (يصرف مستحقاته فقط).
2. إن كان `frozen` ينمو: زر **إعادة تشغيل المجمد** — لكن اقرأ سبب الخطأ أولاً (أودوو ساقط؟ توكن منتهي؟).
3. إن كان عميل واحد يغرق الطابور: قاطع الدائرة يركنه تلقائياً — تحقق من `circuitBreakers` وعالج أودوو الخاص به.
4. إن كان `orphans` ينمو: **استرجاع الأيتام** من `/app/queue` (أو اربط المتجر لتُسترد طلباته).
5. إن كان الأرشيف (`dead`) ينمو: زر **إعادة الكل** (بدل صفاً صفاً).
6. الملاذ الأخير: `GET /api/cron/sync-queue?batch=100` بتوكن `CRON_SECRET` (حلقة 40 ثانية).

## 4) البروفة: `POST /api/admin/load-rehearsal` (أدمن + `confirm:true`)

- `mode=enqueue` آمن في كل مكان (صفوف بعيدة الاستحقاق ثم حذف — لا تلمس أودوو).
- `mode=drain` خارج الإنتاج فقط (تصريف حقيقي ضد أودوو التجريبي)، وفي
  الإنتاج مرفوض إلا بـ `allowProductionDrain:true`.
- سجّل `insertsPerSec` وزمن تصريف 20 ألف كخط أساس قبل الموسم.

## 6) ما الذي يبقى خارج قدرتنا (بصراحة)

- **سقف زد 60 قراءة/دقيقة**: ميزانية السحب تحترمه (فلا 429 ولا ضياع)، لكن
  1000 طلب/دقيقة من متجر واحد **لا يمكن** سحبه كلها — الطلبات تتأخر.
- **سقف أودوو العميل**: كل كتابة XML-RPC تذهب لسيرفر العميل. عميل صغير على
  استضافة مشتركة يحدّه سعة جهازه.
- ⇒ **الطلب المؤجل أفضل من الطلب الضائع**: الطلب يبقى محفوظاً في
  `webhook_inbox`/`sync_queue`، يُعالج تلقائياً، ويُرى في `/app/queue`.
