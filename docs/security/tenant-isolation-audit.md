# Tenant isolation audit

Reviewed 2026-11-03 against the local working tree. This is source inspection and offline mocked verification, not a production database/RLS audit. Pre-existing architecture extractions and sync-log changes were preserved.

## Actual ownership model

Clerk user IDs are strings. A workspace is the tenant boundary: `workspaces.user_id` is its owner, and `workspace_members` permits several users per workspace and one user in several workspaces. `users.active_workspace_id` is a selection, not authority. `setActiveWorkspace` in `src/app/actions/workspaces.ts` checks owner or member before changing the selection. Merchant token tables, ERP connections, mappings, queue events, and sync logs carry workspace references. Runtime clients use Supabase REST service-role credentials; application filters are security boundaries because service-role operations bypass RLS. SQL migrations are evidence of intended constraints, not evidence that a deployed database has applied them.

The ordinary client in `src/lib/supabase.ts` and the independent client in `src/lib/sync-runtime.ts` both use service role. The former adds an impersonation write guard. Odoo merchant XML-RPC and ERPNext REST clients are instantiated for each selected connection; the environment-configured Odoo helpdesk client is a separate support integration.

The application-level ownership requirement is consistent with [Supabase's RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security): service-role access bypasses RLS. The Supabase changelog index was also inspected read-only; no dependency/version change is part of these scoped query fixes. Deployed database policies, versions and TLS settings were not inspected.

## Reviewed protections and limits

- `src/app/actions/sync-logs.ts`: list, detail, statistics, manual resolve and retry log lookup include the active workspace; custom mapping retry lookup also includes workspace. Lean list columns continue excluding payload and error text. This file had a pre-existing diff, preserved here.
- `odoo-client.ts`: UID cache key includes URL, database, username and key fingerprint. Reused HTTP agents are transport pools and carry no shared RPC credential state. Version cache is URL scoped because server version is endpoint metadata. No evidence here supports a last-user credential singleton claim.
- `odoo_entity_links` has a unique `(workspace_id,platform,store_id,odoo_model,store_entity_id)` key in migration `20261011_odoo_entity_links.sql`. It does not include ERP connection identity; replacing the connection within a workspace requires a migration/reconciliation policy for old links. Cross-workspace foreign keys alone do not prove parent-child tenant equality.
- A workspace commonly resolves one ERP connection via `maybeSingle()`. Do not claim two independently routed ERP connections per workspace are supported solely because mappings contain a connection ID. See the routing audit.
- Background jobs are service operations and have no Clerk session. Their payload/connection relationships must be checked at execution, independently of the browser workspace helper. No blanket line-by-line proof of every server action or all deployed RLS policies is claimed.

## Follow-up execution-target hardening

The subsequent authorized implementation adds a pinned `(erp_connection_id, connection_generation)` to durable jobs/receipts and connection-bound matching. `erp-execution-target.ts` verifies the current token ownership for commerce stores, verifies the connection's workspace/status, and hashes configuration affecting authority (including encrypted credentials) into a generation. Credentials are never printed by this helper. A queued job with no pin, a replaced/disabled connection, a changed generation, a foreign mapping or a moved store is refused for controlled recovery. Odoo triggers have no commerce token row: their ingress scope and mapping check, followed by workspace/connection validation in the outbound worker, provide that boundary.

`processWebhookEvent` validates the target before enrichment and mapping lookup; `processSingleMapping` checks inherited workspace/store/platform and explicit mapping connection. Both custom and preset value construction/writes run inside independent async contexts for effect reservations. Outbound record and stock workers compare the selected connection and generation again before constructing a client. Log writes add the connection/generation/platform; matching excludes legacy unpinned logs and links. Manual retry preserves the stored target and refuses legacy logs requiring reconciliation. Pending-order creation no longer invokes/deletes another queue job outside the claimed worker.

Additional mocked executable tests in `erp-execution-target.test.ts` exercise three concurrent target contexts, wrong tenant/store, credential rotation, disabled/deleted connection and stale links. `engine-three-tenant-routing.test.ts` invokes the real mapping engine concurrently and asserts the exact URLs/databases/usernames/decrypted credential values passed to the mocked A/B Odoo and C ERPNext constructors; it also proves a changed mapping constructs neither provider client. This is credential routing evidence, not a real ERP business-effect load test. `entity-links.test.ts` retains prior scope checks and additionally asserts connection/generation scope. `engine-queue-ownership.test.ts` pins removal of opportunistic queue execution/deletion.

These changes require the coordinated reliability schema migration. Historical null-target rows must be reconciled explicitly and must not be silently assigned to the current connection. SQL schema and deployment verification are owned by the lead report. No provider account, live token, dependency or UI was modified by this agent.

The outbound record worker now resolves the platform from a unique token row owned by the mapping's workspace. The previous event-prefix rule classified Zid `product.create`/`order.create` as Salla because it accepted every `product.*`/`order.*`. Ambiguous identities shared by two platforms fail closed for controlled repair rather than selecting credentials by convention. `resolveOwnedStorePlatform` is tested for Zid/Salla and ambiguity. Mapping actions also validate ownership before any webhook registration/removal; deletion scopes the referenced ERP connection by workspace (`mapping-action-isolation.test.ts`, two executable cases).

The latest focused target/engine/link/runtime/action run passed 35 tests in 7 suites. Separate auth/user/access and OAuth/Clerk tests also passed as described above. At this checkpoint `npm run type-check` passed. Final whole-project gates may include further coordinated edits and must be reported by the lead.

Manual mappings with ERP record IDs belong to their destination database. When settings select a different server/database, `switch_erp_mapping_destination` checks the saved connection and serializes the change for that workspace. It archives static mappings and prior settings, clears ERP record references from standard settings, and retires custom mappings while retaining their logs. Store and workspace identity stay attached to every receipt. A queued job keeps its original connection and generation. Outbound Odoo stock webhooks registered for a new destination authenticate with a resource-scoped credential.

The registry regression tests cover changed URL/database/connection ID on new events and first-workspace insert/reread without overwriting an existing baseline. Standard Odoo presets now return without constructing XML-RPC clients for non-Odoo connections; explicit ERPNext custom mappings continue through the ERPNext engine. The guard has a source-order assertion with a negative self-check. Updated manual-retry fixtures preserve actual target validation and additionally prove legacy unpinned/rotated credentials construct no retry effect. The retry/read-speed subset passed 38 tests, and the target/routing/out-of-order subset passed 22 tests; whole-project final results remain in the lead report.
