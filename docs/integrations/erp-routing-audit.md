# ERP routing and effect safety audit

Reviewed 2026-11-03 using local source and mocked transports. This is not a live merchant/ERP certification. Pre-existing architecture extraction changes were preserved. No provider requests, deployments or database migrations were performed.

## Actual execution and identity

Inbound Zid/Salla events enter their platform route, resolve token ownership to a workspace, persist through inbox/queue, then `processWebhookEvent` in `src/lib/sync-engine.ts`. Custom mappings enter `processSingleMapping`; preset events enter `processFixedMappingFallback`, which constructs a virtual mapping. The custom path selects `erp_connections`, decrypts that row, then constructs an event-local `OdooClient` or `ErpNextClient` based on `erp_type`. The preset path currently builds Odoo metadata/values directly and does not provide equivalent ERPNext support.

`workspace_id` is the tenant boundary; Clerk user IDs and workspace membership are distinct. A mapping carries `erp_connection_id`, while default preset/stock/manual transfer paths select by workspace. `startInitialTransfer` rejects non-Odoo connections; ERPNext is not a complete equivalent destination for every application flow. The source does not establish a general explicit store-to-connection association for every flow or prove multiple ERP connections per workspace are consistently supported.

Odoo outbound record processing uses `runBackgroundSync` in `src/app/api/webhooks/odoo/route.ts`: reread mapping, connection, and authoritative ERP values, then platform write. Stock processing in `src/lib/stock-sync-engine.ts` selects the workspace connection. Pending queue events carry workspace/store rather than a versioned immutable ERP connection binding; current mapping selection can change their destination.

## Findings and dispositions

Executable regression failed before patch. This is a missing defensive ownership boundary; malicious browser creation of such a mapping is not claimed proven. | Filter by both ID and workspace. Do not decrypt a foreign connection. Low risk; invalid legacy relationships now fail rather than execute. |

| High, fixed locally | `processFixedMappingFallback` and outbound `runBackgroundSync`: connection-by-ID fetch omitted workspace. | Inconsistent saved mapping relationship could select another workspace's secrets. | Add workspace predicate at both lookups. | High, open | `findExistingOdooRecord`: early `sync_logs` lookup filters workspace/entity/model/status and optional store, but not platform or connection. `odoo_entity_links` key excludes ERP connection. | Coincident source IDs across platforms, or switching ERP database with coincident numeric record IDs, can resolve an unrelated existing ERP record. Broader debug/error redaction and explicit retention/access policy remain open. |

`ErpNextClient` keeps URL/auth on each instance. `OdooClient` keeps config/UID on the instance and globally caches UID by URL/database/user/key fingerprint; version is cached by URL. Shared HTTP agents contain socket pools rather than shared credentials. No last-used global ERP client was found in these inspected paths. The credential cache key uses separator-concatenated strings and a truncated hash, so this review does not constitute a cryptographic uniqueness proof.

## Verification performed

`tests/unit/erp-routing-isolation.test.ts` exercises the real `processSingleMapping` with mocked sync runtime and a decrypt mock that throws if foreign credentials are accessed. Before patch: two failures and one pass. After patch: three passes, covering foreign connection, deleted explicit target, and preserved unconfigured workspace fallback.

`tests/unit/erp-client-concurrency.test.ts` interleaves 100 and 1,000 actual client method calls across Odoo A, Odoo B and ERPNext C with mocked XML-RPC/fetch. Every response is checked against expected host/database/key or authorization header; count is exact. Both cases pass. This establishes client argument separation under async interleaving; it is not an end-to-end webhook/worker/load throughput test or proof of queue recovery/business idempotency. All transports are mocked and the separate `sync-runtime` Supabase client is mocked explicitly.

`tests/unit/odoo-create-unknown-outcome.test.ts` adds three transport-error cases (timeout, socket hangup, reset), each asserting exactly one create, and a confirmed XML-RPC settings rejection case preserving retry/follow-up write. Combined focused run: three suites, nine tests passed. Full gates are recorded by the lead in the final reliability report. Remaining unverified scenarios include actual ERP commit then lost response, multi-process concurrency, connection replacement while queued, disabled connections, external rate limits, live migrations and actual server network egress policy.

## Safe next stages

First define connection replacement and queued-event binding policy, then preflight existing mapping/connection ownership offline in an isolated database snapshot. Plan connection-aware links and effect reservations with backup, dry-run row counts, backfill verification and rollback before any schema deployment. Use provider-specific reference queries for unknown outcomes; inability to identify an external result must require explicit recovery rather than a speculative new create. Test complete route-to-worker routing for three tenants and multiple stores before claiming all destination isolation acceptance criteria.

## Follow-up implementation in this review

After the initial findings, the user authorized the additional reliability implementation and database/test scope. The lead's final report supersedes the initial open/fixed disposition table where later work changed it.

`src/lib/erp-effect-context.ts` now provides trusted execution context through Node AsyncLocalStorage and a durable `erp_effects` reservation before a remote create. Odoo generic `execute(..., 'create', ...)` and ERPNext `create` call the wrapper. Unique insert failure is handled explicitly: a persisted success returns its remote ID, a confirmed rejection may be reclaimed atomically, and an in-progress/uncertain result blocks another create. There is no lease expiration that authorizes repeating an ambiguous write. Missing schema/storage failure prevents the write. Failure or zero returned rows when saving a remote result becomes `ERP_OUTCOME_UNKNOWN`, so local persistence loss cannot authorize another create.

Main create identity includes workspace, platform, store, ERP connection, source entity and model; main values and credential generation are deliberately excluded so changed price/status or credential rotation cannot bypass an uncertainty reservation. Execution generation still fences queued authority, and the resource baseline blocks replacing the ERP server/database. Separate-product variants explicitly pass variant identity through `safeCreateOdooRecord`. Related creates use ordinal and canonical values. That fallback does not prove identity across changed execution order or changed related payloads, and operations invoked without trusted context retain legacy behavior. Succeeded-create replay returns the saved ID; changed create values are not automatically written by the effect wrapper. Business update handling remains in the existing engine.

`tests/unit/erp-effect-context.test.ts` has eight execution tests: reservation storage failure prevents remote calls; remote success followed by result storage failure blocks replay; committed write/lost reply blocks recreation despite changed values; 100 concurrent duplicates issue one remote create; persisted results survive context recreation; tenant/connection/explicit variant identity remains separate; a confirmed rejection may retry; and parent plus two same-model product variants remain three distinct IDs on a price-change replay. The ledger is an in-memory database mock in these tests, not evidence of deployed SQL atomicity, process crash recovery on real Postgres, or external ERP behavior. The lead owns migration staging and additional database validation.

Additional execution tests cover an existing best-effort relation helper swallowing an uncertain create exception and credential rotation after an uncertain write: the execution cannot settle successfully, issue later creates or reset the business reservation by changing credentials. The effect suite therefore has ten cases.

Zid order reconciliation now uses per-workspace/store/connection-generation state, a persisted fixed time window and page cursor, oldest-attempt fairness, at most four list calls and 100 dispatched items per invocation. Each store receives one page per invocation. A full page retains the next page; only a short final page advances that store's watermark to the fixed window end. Dispatch failure retains the current page for safe replay. This requires the staged `sync_reconcile_state.cursor` column. `tests/unit/reconciliation-recovery.test.ts` passes four cases covering six-store fairness, 75-order pagination across invocations, partial dispatch failure and the global item cap. The first scan for a new scope still starts from the configured lookback window; this is not an unlimited historical backfill or recovery of product/customer/category webhooks.
