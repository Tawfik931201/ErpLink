# المواصفة — Spec 001: التبسيط والتكامل (Simplify & Integrate)

- **الحالة:** مسودة نشطة (draft)
- **النطاق:** تبسيط تجربة الربط + إلغاء الأفلييت + دفع يدوي + متطلبات المنصات
- **مرجع الدستور:** `.specify/memory/constitution.md`

## 1. الخلفية

التطبيق (erplink) يربط Odoo بمتاجر Zid/Salla/Shopify. تراكم عبر الوقت:
نظام أفلييت كامل، بنية تنقل من 9 أقسام، ومعالج ربط طويل — النتيجة احتكاك يمنع
هدف **"الربط في 3 دقائق"**. هذه المواصفة تجمّد القرارات المطلوبة للتبسيط.

## 2. المتطلبات الوظيفية (FR)

### FR-1 — إلغاء الأفلييت
- FR-1.1: حذف كل واجهات الأفلييت (صفحات `/partners`، `/partner/*`، `/admin/partners`،
  `/admin/commissions`، `/admin/payouts`) إن وُجدت بقاياها.
- FR-1.2: إيقاف Server Actions والـ API الخاصة بالعمولات والصرف
  (`addCommission`، `reviewPayoutRequest`، `api/partner/request-payout`).
- FR-1.3: تجميد جداول `partner_*` — لا كتابة جديدة؛ الإبقاء للقراءة التاريخية فقط.
- FR-1.4: إزالة نصوص `partners.*` و `admin.partners.*` من `translations.ts`.
- معيار القبول: لا مسار ولا زر ولا ترجمة يذكر الأفلييت؛ `type-check` أخضر.

### FR-2 — الدفع اليدوي
- FR-2.1: الأدمن فقط يسجّل/يمدّد/يلغي الاشتراك (`subscription-actions.ts` موجودة — إبقاء).
- FR-2.2: كل عملية دفع تُسجَّل: المبلغ + العملة + الأشهر + `created_by` + التاريخ.
- FR-2.3: `end_date = start_date + months − 1 day` هو مصدر الحقيقة للحالة.
- FR-2.4: بطاقة الحالة + بانر انتهاء الصلاحية (كهرماني ≤7 أيام، أحمر عند الانتهاء،
  قابل للصرف عبر X مع `sessionStorage`).
- معيار القبول: دورة كاملة (تسجيل → تمديد → إلغاء) من لوحة الأدمن مع سجل تدقيق.

### FR-3 — تبسيط IA من 9 إلى 5
- FR-3.1: الحد الأقصى 5 أقسام رئيسية في التنقل (مقترح: لوحة القيادة، الطلبات،
  المنتجات/المخزون، التكاملات، الإعدادات).
- FR-3.2: دمج الشاشات المكررة وإخفاء المتقدم تحت "إعدادات متقدمة".
- FR-3.3: كل قسم يصل لهدفه الأساسي بنقرتين كحد أقصى من اللوحة.
- معيار القبول: خريطة تنقل موثقة + لا طريق مسدود (404) من عناصر محذوفة.

### FR-4 — معالج الربط 3 خطوات
- FR-4.1: الخطوة 1 — اختيار المنصة (Zid/Salla/Shopify) وبدء OAuth.
- FR-4.2: الخطوة 2 — اختيار مساحة العمل في Odoo ومراجعة الصلاحيات.
- FR-4.3: الخطوة 3 — تأكيد وتشغيل أول مزامنة تجريبية (`api/test-sync`).
- FR-4.4: مؤقّت مرئي يستهدف إتمام الربط خلال 3 دقائق + معالجة أخطاء واضحة لكل خطوة.
- معيار القبول: مستخدم جديد يربط متجراً تجريبياً في ≤3 دقائق في بيئة اختبار.

### FR-5 — متطلبات المنصات
- FR-5.1 (Shopify GDPR): مستقبلات webhooks الإلزامية
  (`customers/data_request`، `customers/redact`، `shop/redact`) ترد `200` وتُسجَّل في التدقيق.
- FR-5.2 (Salla scopes): طلب الحد الأدنى من الصلاحيات عند OAuth وتوثيق كل scope وسبب الحاجة إليه.
- FR-5.3 (Zid مرتجعات): دعم تدفق المرتجعات من زد إلى Odoo (الحالات + عكس حركة المخزون)
  مع اختبار end-to-end على بيئة تجريبية.
- معيار القبول: قائمة تحقق لكل منصة موقّعة باختبار ناجح.

## 3. متطلبات غير وظيفية (NFR)

- NFR-1: `npm run type-check` و `npm run lint` خضراوان بعد كل تغيير.
- NFR-2: كل كتابة DB عبر عميل service_role؛ لا كتابة من العميل مباشرة.
- NFR-3: كل عملية حساسة في `audit_logs`.
- NFR-4: ثنائية اللغة (ar/en) لأي نص جديد.

## 4. خارج النطاق (Out of scope)

- بوابات دفع آلية (Stripe موجود كاعتمادية لكنه خارج التفعيل في هذا الطور).
- إعادة تسمية جداول `partner_*` في قاعدة البيانات (تجميد فقط).
- تطبيقات جوال أصلية.

## 5. المخاطر والافتراضات

| الخطر | التخفيف |
|---|---|
| بقايا أفلييت في DBs قديمة تُربك المطورين | توثيق "مهجور" + عدم البناء عليها (FR-1.3) |
| تقليل IA يكسر روابط محفوظة | خرائط تحويل (redirects) للمسارات المحذوفة |
| تغيير scopes سلة يقطع تكاملات قائمة | إعلان + إعادة مصادقة تدريجية |
